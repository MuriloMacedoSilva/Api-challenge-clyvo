# DDL Oracle 19c do CLYVO

## Propósito

`script_bd_oracle.sql` define as 14 tabelas correspondentes às entidades JPA atuais. O profile Spring Boot `oracle` permite executar a mesma API sobre Oracle Database 19c sem substituir os profiles PostgreSQL ou H2.

Segundo o inventário institucional fornecido ao projeto, o arquivo foi executado com sucesso no schema `RM566462` e criou os 14 objetos planejados. Esta atualização Java não abriu conexão com esse ambiente nem executou DDL ou DML. O arquivo não contém dados, `DROP`, `TRUNCATE`, packages, procedures, functions ou triggers. O SQL acadêmico original em `../../../database/2TDSA_2024_CodigoSql_Integrantes.sql` permanece separado e inalterado.

O DDL PostgreSQL atual possui as mesmas 14 tabelas das 14 classes com `@Entity`. Foram conferidos os nomes físicos, colunas, nulabilidade, identidades, enums, relacionamentos, `@OrderColumn`, constraints únicas e índices. A ordem do DDL Oracle respeita todas as dependências de FK.

## Adaptações do PostgreSQL para Oracle

| PostgreSQL/JPA | Oracle 19c proposto | Observação |
|---|---|---|
| `bigint identity` | `NUMBER(19,0) GENERATED BY DEFAULT AS IDENTITY` | Aceita IDs gerados e importações controladas com ID explícito. |
| `integer` | `NUMBER(10,0)` | Usado para idade e ordem dos itens. |
| `real` | `FLOAT(24)` | Precisão aproximada semelhante, mas Oracle `FLOAT` é subtipo de `NUMBER`, não IEEE-754. |
| `boolean` | `NUMBER(1,0)` + check `IN (0,1)` | Oracle 19c não possui tipo SQL `BOOLEAN` para colunas. |
| `timestamp(6) without time zone` | `TIMESTAMP(6)` | Preserva a semântica local de `LocalDateTime`, sem fuso. |
| `date` de vacinação | `DATE` | O driver deve mapear `LocalDate`; Oracle `DATE` também comporta hora. |
| `text` de `Animal.history` | `CLOB` | Oracle não possui tipo `TEXT`. |
| `varchar(n)` | `VARCHAR2(n CHAR)` | Preserva o limite lógico JPA em caracteres, sujeito ao teto físico de 4000 bytes. |
| Índice parcial de unread | Índice composto incluindo `IS_READ` | Oracle 19c não oferece `CREATE INDEX ... WHERE`. |

Com `MAX_STRING_SIZE=STANDARD`, tanto `VARCHAR2(4000 CHAR)` quanto `VARCHAR2(2000 CHAR)` são declarações válidas no Oracle 19c. O número declarado não pode ultrapassar 4000, independentemente de `BYTE` ou `CHAR`. Nenhuma definição do DDL ultrapassa esse limite e, portanto, não há declaração conhecida que cause `ORA-00910` durante o `CREATE TABLE`.

O teto do valor armazenado continua sendo 4000 bytes. Em `AL32UTF8`, um caractere pode consumir de 1 a 4 bytes. Assim, `CHAR` preserva a validação lógica de quantidade de caracteres, mas não garante que toda combinação possível até o limite declarado caiba fisicamente. Um valor que respeite a quantidade de caracteres, mas ultrapasse 4000 bytes, será rejeitado normalmente com `ORA-12899`; Oracle não o trunca silenciosamente.

`AL16UTF16` não afeta este DDL porque nenhuma coluna usa `NCHAR`, `NVARCHAR2` ou `NCLOB`.

As colunas expostas a essa diferença são:

| Tabela.coluna | Declaração | Limite JPA atual |
|---|---|---|
| `TB_MEDICAL_RECORDS.DESCRIPTION` | `VARCHAR2(4000 CHAR)` | 4000 caracteres |
| `TB_MEDICAL_RECORDS.OBSERVATIONS` | `VARCHAR2(4000 CHAR)` | 4000 caracteres |
| `TB_PRESCRIPTIONS.INSTRUCTIONS` | `VARCHAR2(4000 CHAR)` | 4000 caracteres |
| `TB_EXAMS.RESULT` | `VARCHAR2(4000 CHAR)` | 4000 caracteres |
| `TB_EXAMS.OBSERVATIONS` | `VARCHAR2(4000 CHAR)` | 4000 caracteres |
| `TB_VACCINATIONS.OBSERVATIONS` | `VARCHAR2(4000 CHAR)` | 4000 caracteres |
| `TB_MESSAGES.CONTENT` | `VARCHAR2(2000 CHAR)` | 2000 caracteres |

Em cenário extremo com caracteres de 4 bytes, o teto físico pode ser atingido com aproximadamente 1000 caracteres. Trocar essas colunas para `CLOB` seria a única forma de garantir os limites lógicos completos para qualquer conteúdo Unicode, mas exigiria alteração coordenada das entidades e do DDL. O schema atual mantém `VARCHAR2(... CHAR)` e registra o risco para decisão futura.

O uso de `FLOAT(24)` deve ser testado com valores limítrofes, arredondamento e o driver JDBC escolhido. PostgreSQL `real` e Java `Float` seguem IEEE-754, enquanto Oracle `FLOAT` usa a representação numérica do Oracle e não preserva valores especiais como `NaN` e infinito com a mesma semântica.

As colunas de vacinação usam `DATE` por ser o tipo Oracle compatível com `LocalDate`, mas `DATE` também armazena hora, minuto e segundo. A API deve persistir essas datas sem componente de hora; importações externas precisam aplicar a mesma regra para não divergir do PostgreSQL `date`.

Oracle trata string vazia (`''`) como `NULL`. A aplicação já normaliza muitos textos clínicos opcionais, mas campos obrigatórios devem continuar sendo validados antes da persistência. Um valor vazio em coluna `NOT NULL` falhará como `NULL`, diferentemente do PostgreSQL.

## Profile Java Oracle

O profile `oracle` está configurado em `src/main/resources/application-oracle.properties` com:

- `ojdbc11` `23.9.0.25.07` em runtime, versão gerenciada pelo Spring Boot e compatível com Java 21 e Oracle 19c;
- `OracleDialect` explícito e `spring.jpa.hibernate.ddl-auto=validate`;
- `spring.sql.init.mode=never`, sem seed, criação automática ou migration;
- credenciais exclusivamente pelas variáveis obrigatórias `ORACLE_DB_URL`, `ORACLE_DB_USERNAME` e `ORACLE_DB_PASSWORD`;
- pool pequeno por padrão, timeouts de conexão/leitura e falha rápida configuráveis pelas variáveis `ORACLE_*` documentadas em `.env.example`;
- SQL, formatação SQL e console H2 desabilitados.

`Animal.history` usa `@JdbcTypeCode(SqlTypes.LONG32VARCHAR)`. No Hibernate 7.2 esse tipo materializado gera `text` no PostgreSQL e `CLOB` no Oracle/H2, mantendo a propriedade Java como `String`. `@Lob` não foi usado porque o dialect PostgreSQL o associaria a `oid`, incompatível com a coluna `text` existente.

Os demais mapeamentos foram preservados. O `OracleDialect` representa `boolean` como `NUMBER(1,0)`, `Long` como `NUMBER(19,0)` e `Float` como `FLOAT(24)`, em alinhamento com o DDL. A validação de startup confirmou a compatibilidade estrutural; identities em DML, `LocalDate`, paginação, locks e transações ainda dependem de execução controlada no Oracle real.

O profile já foi inicializado com sucesso no Oracle institucional: conexão JDBC, schema `RM566462`, Hibernate 7.2.12, validação de schema e criação do `EntityManagerFactory` concluíram sem erro. Isso valida a compatibilidade estrutural de startup, mas não substitui CRUD, transações e relacionamentos reais. O roteiro controlado está em `database/README-oracle-crud-tests.md`.

Os campos de 2000/4000 caracteres continuam sujeitos ao teto Oracle de 4000 bytes descrito acima. Migrá-los para `CLOB` exige alteração coordenada do DDL e do mapeamento, não uma mudança isolada no profile.

### Inicialização manual da API

Definir as variáveis somente na sessão local autorizada. A senha pode ser lida sem aparecer no histórico do shell:

```bash
export SPRING_PROFILES_ACTIVE=oracle
export ORACLE_DB_URL='jdbc:oracle:thin:@//host:1521/service-name'
export ORACLE_DB_USERNAME='usuario-do-schema'
read -rs ORACLE_DB_PASSWORD && export ORACLE_DB_PASSWORD
./mvnw spring-boot:run
```

No Docker, o entrypoint não executa `psql` quando o profile ativo inclui `oracle`; a conectividade e o schema são validados pelo driver, Hikari e Hibernate. O `docker-compose.yml` continua dedicado ao PostgreSQL local e não recebe credenciais Oracle.

### Protocolo de teste controlado

Executar somente após autorização para conectar e alterar dados no schema:

1. Confirmar que a API inicia sem erro de `Schema-validation`; qualquer divergência deve interromper o ensaio, sem `ALTER`, `CREATE` ou `DROP` automático.
2. Confirmar `GET /tutor/ping` e a geração do OpenAPI sem inserir dados.
3. Em massa descartável aprovada, cadastrar Tutor, Veterinário e Animal sem informar IDs e confirmar IDs gerados pelas identities.
4. Exercitar um CRUD representativo e reler os valores, incluindo `Animal.history`, booleanos, `LocalDate`, `LocalDateTime`, enums e textos Unicode.
5. Exercitar consultas com `PageRequest`/limites, ordenações e o lock pessimista das transições de Exam.
6. Provocar uma falha de validação dentro de um caso de uso transacional e confirmar que nenhuma alteração parcial ou Notification ficou persistida.
7. Remover somente a massa descartável criada pelo ensaio, pelos endpoints autorizados; não limpar nem alterar registros preexistentes.

Os testes automatizados locais verificam o carregamento das propriedades sem conexão Oracle, a presença do driver e a persistência H2 de `Animal.history` com 40.000 caracteres. Eles não substituem este protocolo no Oracle 19c.

O DDL não adiciona unicidade para CPF, e-mail, CRMV ou CNPJ porque as entidades e o DDL PostgreSQL atuais não a declaram. Alterar essa integridade exige decisão funcional, inspeção de dados e mudança coordenada, não uma divergência silenciosa apenas no Oracle.

## Preservação do modelo acadêmico

Os objetos acadêmicos devem permanecer separados durante esta fase:

| Objeto acadêmico | Destino futuro recomendado |
|---|---|
| `TB_TUTOR` | Migrar dados, após transformação, para `TUTOR`; faltam senha e papel. |
| `TB_VETERINARIO` | Migrar para `VETERINARIAN`; separar CRMV em número/UF e complementar CPF, telefone, senha, papel e CNPJ. |
| `TB_ANIMAL` | Migrar para `ANIMAL`; converter nascimento em idade conforme regra definida e complementar altura/histórico. |
| `TB_VACINACAO` | Migrar para `TB_VACCINATIONS`; remapear FKs e adicionar timestamps. |
| `TB_FATO_ATENDIMENTO` | Preservar como extensão analítica/financeira ligada futuramente a `TB_APPOINTMENTS`. |
| `TB_AUDITORIA_VACINACAO` | Preservar como extensão de auditoria futura de `TB_VACCINATIONS`. |

`TB_FATO_ATENDIMENTO` não equivale a `TB_APPOINTMENTS`: não possui Animal, Tutor ou status e armazena valor e espécie desnormalizada. Uma evolução segura deve referenciar `TB_APPOINTMENTS.ID`, definir se representa cobrança ou fato analítico e tratar espécie como snapshot deliberado.

`TB_AUDITORIA_VACINACAO` pode evoluir para snapshots completos de `TB_VACCINATIONS`. A retenção após exclusão precisa ser definida antes de criar FK, e a auditoria deve registrar fabricante e observações, omitidos pela trigger acadêmica atual. Nenhuma trigger é criada nesta fase.

Functions, procedures e trigger do trabalho acadêmico referenciam as tabelas acadêmicas antigas. Packages futuros devem ser adaptados para as tabelas e colunas canônicas somente depois da implantação e da estratégia de migração de dados; não devem criar um segundo cadastro operacional.

## Pré-verificação obrigatória

Oracle executa DDL com commits implícitos. Portanto, a verificação deve ocorrer antes da execução, na mesma conta que será proprietária dos objetos.

Esta seção se aplica a uma implantação nova ou recuperação formalmente aprovada. Como as 14 tabelas já foram informadas como criadas no schema institucional, não se deve repetir o DDL nesse schema; usar as consultas de validação pós-execução para inventariar o estado atual.

Todas as consultas desta seção são somente leitura.

### 1. Confirmar conta, versão e parâmetros relevantes

```sql
SELECT banner_full FROM v$version WHERE banner_full LIKE 'Oracle Database%';
SELECT username, default_tablespace, temporary_tablespace, account_status
  FROM user_users;
SELECT parameter, value
  FROM nls_database_parameters
 WHERE parameter IN ('NLS_CHARACTERSET', 'NLS_NCHAR_CHARACTERSET', 'NLS_LENGTH_SEMANTICS');
SELECT value FROM v$parameter WHERE name IN ('compatible', 'max_string_size');
```

O resultado deve confirmar o schema `RM566462`, `AL32UTF8`, `AL16UTF16` e `MAX_STRING_SIZE=STANDARD`. O acesso a `V$VERSION` ou `V$PARAMETER` pode ser restrito no ambiente institucional. Nesse caso, usar os valores já fornecidos pela FIAP ou solicitar confirmação ao responsável, sem tentar elevar privilégios.

### 2. Confirmar privilégios efetivos

```sql
SELECT privilege
  FROM session_privs
 WHERE privilege IN (
    'CREATE TABLE', 'CREATE SEQUENCE', 'CREATE VIEW',
    'CREATE TRIGGER', 'CREATE PROCEDURE', 'UNLIMITED TABLESPACE'
 )
 ORDER BY privilege;

SELECT privilege, admin_option
  FROM user_sys_privs
 ORDER BY privilege;
```

Os cinco privilégios informados devem aparecer para confirmar o inventário institucional. Para este DDL específico, o bloqueio relevante é a ausência de `CREATE TABLE` ou de espaço utilizável; procedures, triggers e views não são criadas nesta fase. `UNLIMITED TABLESPACE` é opcional se houver quota suficiente no tablespace padrão.

### 3. Confirmar quota e espaço visível

```sql
SELECT tablespace_name,
       bytes AS used_bytes,
       max_bytes,
       CASE
           WHEN max_bytes = -1 THEN NULL
           ELSE max_bytes - bytes
       END AS quota_remaining_bytes
  FROM user_ts_quotas
 ORDER BY tablespace_name;

SELECT tablespace_name,
       SUM(bytes) AS free_bytes,
       MAX(bytes) AS largest_free_extent_bytes
  FROM user_free_space
 GROUP BY tablespace_name
 ORDER BY tablespace_name;

SELECT tablespace_name, status, contents, extent_management,
       allocation_type, segment_space_management
  FROM user_tablespaces
 ORDER BY tablespace_name;
```

A implantação pode prosseguir com quota finita suficiente no tablespace padrão ou com `UNLIMITED TABLESPACE`. A combinação de linha ausente em `USER_TS_QUOTAS` e ausência de `UNLIMITED TABLESPACE`, quota restante insuficiente ou tablespace indisponível deve ser tratada com o responsável institucional. `USER_FREE_SPACE` mostra apenas extents visíveis e não informa de forma completa o limite de autoextend dos datafiles; sem acesso às views `DBA_*`, essa capacidade final precisa ser confirmada pelo administrador.

### 4. Procurar tabelas e outros objetos canônicos

```sql

  FROM user_objects
 WHERE object_name IN (
    'TUTOR', 'VETERINARIAN', 'ANIMAL', 'TB_DEVICE_PUSH_TOKENS',
    'TB_VETERINARIAN_TUTOR_LINKS', 'TB_APPOINTMENTS', 'TB_MEDICAL_RECORDS',
    'TB_PRESCRIPTIONS', 'TB_PRESCRIPTION_ITEMS', 'TB_EXAMS',
    'TB_VACCINATIONS', 'TB_NOTIFICATIONS', 'TB_CONVERSATIONS', 'TB_MESSAGES'

```

O resultado esperado para os 14 nomes é vazio. A consulta deve ser repetida imediatamente antes da execução, mesmo que o inventário anterior já tenha confirmado a ausência dessas tabelas.

### 5. Procurar constraints planejadas

```sql
SELECT constraint_name, constraint_type, table_name, status
  FROM user_constraints
 WHERE constraint_name LIKE 'PK\_CV\_%' ESCAPE '\'
    OR constraint_name LIKE 'UK\_CV\_%' ESCAPE '\'
    OR constraint_name LIKE 'CK\_CV\_%' ESCAPE '\'
    OR constraint_name LIKE 'FK\_CV\_%' ESCAPE '\'
 ORDER BY constraint_name;
```

### 6. Procurar índices planejados e nomes reservados para PK/UNIQUE

```sql
SELECT index_name, table_name, uniqueness, status, tablespace_name
  FROM user_indexes
 WHERE index_name LIKE 'IX\_CV\_%' ESCAPE '\'
    OR index_name LIKE 'PK\_CV\_%' ESCAPE '\'
    OR index_name LIKE 'UK\_CV\_%' ESCAPE '\'

```

As PKs e constraints `UNIQUE` normalmente criam índices. Por isso, nomes `PK_CV_*` e `UK_CV_*` também são verificados em `USER_INDEXES`, além dos 17 índices explícitos `IX_CV_*`.

Se qualquer linha for retornada nas verificações de objetos canônicos ou nomes `CV`, interromper. Não executar o DDL, não renomear e não remover o objeto sem identificar estrutura, dados e origem.

## Execução manual após aprovação

Não repetir este procedimento no schema institucional que já contém as 14 tabelas. Ele permanece documentado para ambientes novos e para rastreabilidade da implantação original.

1. Salvar os resultados das consultas de conta, privilégios, quota, objetos, constraints e índices.
2. Prosseguir somente se as consultas de conflito estiverem vazias e houver quota ou `UNLIMITED TABLESPACE`.
3. Executar em uma janela controlada, autenticado como `RM566462`, sem registrar senha em arquivo ou histórico compartilhado.
4. Abrir o cliente sem informar senha na linha de comando. Usar um dos launchers:

```bash
# SQLcl
sql RM566462@servico

# SQL*Plus
sqlplus RM566462@servico
```

5. Já no prompt SQLcl ou SQL*Plus, iniciar o spool e executar em modo script:

```sql
WHENEVER OSERROR EXIT FAILURE
WHENEVER SQLERROR EXIT SQL.SQLCODE
SPOOL clyvo-oracle-first-deploy.log
@Java/api/database/script_bd_oracle.sql
SPOOL OFF
```

Se o diretório corrente já for `Java/api/database`, usar `@script_bd_oracle.sql`.

O DDL configura `WHENEVER OSERROR EXIT FAILURE` e `WHENEVER SQLERROR EXIT SQL.SQLCODE`, além de `ECHO` e `FEEDBACK`, para interromper SQLcl/SQL*Plus no primeiro erro e manter comandos/resultados no log. Ferramentas que ignoram comandos SQL*Plus devem ser configuradas explicitamente para parar no primeiro erro. Não executar como uma seleção parcial de comandos sem registrar exatamente o que foi aplicado.

Não executar `demo-data.sql`, `demo-data-postgres.sql` ou o seed acadêmico nesse schema. Eles não são seeds Oracle operacionais.

## Execução parcialmente concluída

Como Oracle confirma cada DDL implicitamente, um erro pode deixar tabelas e índices já criados. Nessa situação:

1. Interromper imediatamente e preservar o log completo da sessão.
2. Inventariar `USER_OBJECTS`, `USER_TABLES`, `USER_CONSTRAINTS`, `USER_INDEXES` e `USER_TAB_IDENTITY_COLS` usando as consultas acima.
3. Comparar o inventário com a ordem de `script_bd_oracle.sql` e identificar o primeiro comando que falhou.
4. Não executar `DROP`, não reiniciar o arquivo e não inserir dados.
5. Decidir com o responsável pelo schema entre completar somente os comandos ausentes, após corrigir a causa, ou elaborar um rollback revisado e específico. A decisão deve considerar dados que possam ter sido inseridos por terceiros após a criação parcial.
6. Registrar o procedimento aprovado em uma migration/versionamento antes de qualquer ambiente produtivo.

O script é intencionalmente não idempotente. Transformá-lo em blocos que ignoram `ORA-00955` mascararia objetos incompatíveis e não tornaria a implantação segura.

## Package de vacinação compilado e integração preparada

Os arquivos abaixo preparam uma camada PL/SQL read-only separada do DDL das 14 tabelas:

- `pkg_clyvo_vacinacao_spec.sql`: specification de `PKG_CLYVO_VACINACAO`;
- `pkg_clyvo_vacinacao_body.sql`: body com duas functions e duas procedures;
- `validate_pkg_clyvo_vacinacao.sql`: validação posterior somente leitura;
- `README-oracle-pkg-vacinacao.md`: contratos, erros, cursores, instalação, integração Java e validação manual.

O package consulta `TUTOR`, `ANIMAL`, `VETERINARIAN` e `TB_VACCINATIONS` para classificar datas previstas, contar atenções objetivas, listar o histórico de um Animal e montar a agenda de um Tutor. Ele não contém DML, transação explícita, SQL dinâmico, trigger ou autorização baseada em CPF/CRMV. Propriedade do Animal, vínculo `ACCEPTED` e identidade do ator continuam no Java.

O usuário confirmou a execução manual da specification e do body no Oracle institucional. `USER_OBJECTS` retornou `PACKAGE` e `PACKAGE BODY` como `VALID`, e `USER_ERRORS` não retornou erros. Não repetir `script_bd_oracle.sql` para instalar o package.

O backend agora seleciona `OracleVaccinationHistoryReader` somente no profile `oracle` para chamar `PR_HISTORICO_ANIMAL` por `SimpleJdbcCall`; PostgreSQL e H2 continuam com `JpaVaccinationHistoryReader`. Autorização permanece no `VaccinationService`, antes da chamada. A integração Java foi coberta localmente com mocks e H2, mas ainda não foi executada contra o package Oracle real.

## Limites da validação desta fase

Na implementação local do profile foram realizadas inspeção de código, resolução do driver e testes H2 sem abrir conexão Oracle. Posteriormente, a inicialização manual autorizada confirmou a conexão e o `ddl-auto=validate`, sem DDL ou deploy. Uma execução CRUD parcial posterior confirmou ping, cadastro/login de Tutor e cadastro de Animal, mas a leitura dos Animals encontrou uma `LazyInitializationException` na fronteira Service/Controller.

O problema foi corrigido localmente sem alterar mappings, DDL ou o profile Oracle: `TutorService` consulta Animals diretamente, materializa `AnimalResponseDTO` dentro de uma transação read-only e o controller não percorre entidades. A auditoria aplicou a mesma fronteira transacional à listagem de Tutores vinculados. Três testes HTTP com banco H2 isolado e `spring.jpa.open-in-view=false` passaram. A suíte posterior à integração local do histórico vacinal possui 137 testes aprovados. Não houve nova conexão, DML ou limpeza Oracle durante essa implementação, portanto a chamada Java ao package e a releitura institucional permanecem pendentes. As demais identities em DML, datas, paginação, locks, transações e relacionamentos reais continuam condicionadas ao roteiro autorizado de `README-oracle-crud-tests.md`.
