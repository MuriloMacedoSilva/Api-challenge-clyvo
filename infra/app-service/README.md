# CLYVO Java — Terraform e Azure DevOps

Esta é uma **opção separada** do deploy acadêmico ACR/ACI em `azure/` e do Render. O repositório Git do backend tem raiz em `Java/api`; `azure-pipelines.yml` está nessa raiz. Não executar os scripts ACI para preparar o App Service. Nenhum recurso foi criado por estes arquivos.

## Arquitetura e propriedade

`infra/bootstrap (inicial) → state remoto → infra/devops (WIF/connection/group) → infra/access (RBAC) → pipeline GitHub/Azure DevOps → App Service Linux Java SE 21 → PostgreSQL externo durável`. O Resource Group da API é **criado pelo bootstrap** e consultado aqui como data source; um precondition confirma as tags de ambiente/bootstrap e região. Este Terraform cria somente um Linux App Service Plan e um Linux Web App nesse grupo. Não gerencia ACR, ACI, Render, PostgreSQL, .NET, Oracle, MongoDB, RG nem storage do state. Não apontar nomes para um App Service/plan existente sem importação planejada e revisão do state. O RG acadêmico ACI e o banco efêmero não fazem parte deste fluxo.

Um diretório/backend/key e nomes de App Service/plan por ambiente isolam `dev`, `staging`, `prod`. Usar pipelines/service connections e escopos RBAC separados por ambiente (e preferencialmente RGs separados). O módulo exige `environment`, `resource_group_name`, `location`, `app_service_plan_name`, `web_app_name`; SKU inicial `B1`, `tags` opcionais. `https_only`, TLS >= 1.2, FTPS desabilitado, Always On e health check `/tutor/ping`; outputs: nome, ID, hostname e RG. Java SE 21 executa o JAR Spring Boot (Tomcat embutido); não implantar WAR nem imagem Docker. Confirmar disponibilidade de Java SE 21/SKU na região antes de aprovar o plan: `az webapp list-runtimes --os linux` (consulta opcional, somente após autorização para acessar Azure).

## State remoto e bootstrap (manual, fora deste módulo)

Executar uma única inicialização por ambiente via [infra/bootstrap/README.md](../bootstrap/README.md). O bootstrap Terraform cria dois RGs, Storage Account GPv2 e **dois containers privados**: `tfstate` guarda bootstrap (`bootstrap/<ambiente>.tfstate`), integração DevOps (`devops/<ambiente>.tfstate`) e RBAC (`access/<ambiente>.tfstate`); `appstate` guarda somente `app-service/<ambiente>.tfstate`. Ativa TLS, Entra ID/RBAC em vez de chaves compartilhadas, versionamento e soft delete. O próprio state do bootstrap é migrado do local temporário para `tfstate`. [infra/devops/README.md](../devops/README.md) cria identidade, credencial federada, Service Connection e variable group; [infra/access/README.md](../access/README.md) concede acesso da service principal **apenas a `appstate`** e aos recursos Web no RG da aplicação. Os providers não registram recursos automaticamente; administrador deve confirmar `Microsoft.Storage`, `Microsoft.Resources`, `Microsoft.Authorization` e `Microsoft.Web`. Restringir acesso à Service Connection, artefatos, logs e blobs; usar lock nativo do backend e recuperar versões com procedimento controlado. Não armazenar access keys em variáveis, arquivos ou CLI.

`backend "azurerm" {}` é parcial. A pipeline preenche `resource_group_name` e `storage_account_name` dos outputs do bootstrap, `container_name=appstate`, `key=app-service/<ambiente>.tfstate`, `use_oidc=true` e `use_azuread_auth=true` no `terraform init`. **Nunca** configurar `TF_STATE_CONTAINER=tfstate` na pipeline. O mesmo backend/key **imutável** é usado pelo plan e apply na mesma execução. Configuração local sem backend: `terraform -chdir=infra/app-service fmt -check -recursive`; `terraform -chdir=infra/app-service init -backend=false` (baixa provider) e `terraform -chdir=infra/app-service validate`. `.tfstate`, `.tfvars` e `.tfplan` estão ignorados no Git; **state e plan ainda podem conter segredos**, inclusive atributos retornados pela API Azure mesmo com `ignore_changes`. Restringir downloads/retention do plan binário no Azure DevOps. Outputs não incluem credenciais.

Para verificar **cada configuração de forma independente, sem consultar states nem Azure**, na raiz Git do backend e com Terraform instalado:

```bash
for module in bootstrap devops access app-service; do
  terraform -chdir="infra/$module" fmt -check -recursive
  terraform -chdir="infra/$module" init -backend=false -input=false
  terraform -chdir="infra/$module" validate
done
git diff --check
```

`init -backend=false` baixa plugins do registry (exige rede e gera `.terraform/`/lock local) mas não acessa backend remoto. Fixar e versionar os `.terraform.lock.hcl` gerados com revisão das versões antes da primeira execução real para builds reprodutíveis. Os comandos não substituem `terraform plan` autenticado, o teste WIF real nem a revisão de custos.

## Azure DevOps: preparação manual

1. Após bootstrap, executar `infra/devops` e `infra/access` com planos separados/revisados. Conectar **GitHub** ao projeto Azure DevOps e criar uma pipeline YAML usando `azure-pipelines.yml` da raiz do repositório `Api-challenge-clyvo` (não a raiz `challenge`). Informar o ID dessa definição a `infra/devops` e aplicar a autorização restrita da Service Connection e variable group antes de executá-la. Configurar políticas de proteção da branch `main` e revisão de PR; triggers filtram `src/**` (incluindo testes), `pom.xml`, `mvnw`, `mvnw.cmd`, `.mvn/**`, **somente `infra/app-service/**`** e o próprio YAML. Alterações em `infra/bootstrap`, `infra/devops`, `infra/access` ou `azure/` não disparam o fluxo habitual.
2. Instalar/autorizar a extensão **Terraform** que fornece `TerraformInstaller@1`; usar agentes Microsoft-hosted Ubuntu com JDK 21 pré-instalado, JavaToolInstaller, Azure CLI, Python 3 e Maven Wrapper executável. Conferir permissões de uso da extensão e versão pinada no YAML.
3. `infra/devops` cria a **Azure Resource Manager Service Connection WIF** sem client secret na mesma subscription do backend e da aplicação e um variable group não sensível. Operador precisa de identidade/credencial inicial Entra ID e Azure DevOps para executar esse Terraform; `infra/access` usa seu output de object ID para conceder RBAC. **Antes de habilitar CI automático**, substituir os defaults `CONFIGURE_ARM_WIF_SERVICE_CONNECTION` e `CONFIGURE_NON_SECRET_VARIABLE_GROUP` no YAML pelos outputs reais `service_connection_name` e `variable_group_name`, após revisão e proteção de branch; parâmetros informados só ao enfileirar manualmente não configuram pushes futuros. O group é referência obrigatória até para CI; criar e autorizar a definição antes da primeira execução. Os tasks AzureCLI passam token OIDC ao provider/backend; não usar publish profile ou senha do App Service.
4. Conferir variáveis **não sensíveis** criadas por `infra/devops` no variable group autorizado, de acordo com o ambiente. Não deixar strings `$(...)` indefinidas:

   | Variável | Valor a definir |
   |---|---|
   | `TF_STATE_RESOURCE_GROUP`, `TF_STATE_STORAGE_ACCOUNT`, `TF_STATE_CONTAINER`, `TF_STATE_KEY` | Outputs `state_resource_group_name`, `state_storage_account_name`, `app_state_container_name` (`appstate`) e `app_service_state_key` |
   | `TF_RESOURCE_GROUP`, `TF_LOCATION` | Output `app_resource_group_name` e região do bootstrap |
   | `TF_PLAN_NAME`, `TF_WEB_APP_NAME` | Nomes novos; Web App globalmente único |
   | `TF_ENVIRONMENT` | `dev`, `staging` ou `prod` |

   Os nomes da connection, variable group, RG, plano e Web App são entradas reais fornecidas ao Terraform pelo operador; nenhum é inventado pela pipeline. `infra/devops` recebe **outputs verificados** do bootstrap; a pipeline não lê o state do bootstrap. Para SKU/tags, revisar variáveis Terraform; B1 é default. Não reutilizar service connection ou state entre ambientes sem decisão explícita.

5. Após o **apply** aprovado (Web App criado), provisionar banco PostgreSQL 16 **durável e externo** por fluxo separado, aplicar `database/script_bd.sql` ao banco vazio com controle de mudança e validar conectividade do App Service ao host (firewall/TLS/VNet). O profile `prod` usa `ddl-auto=validate`: não cria schema. Configurar App Settings do Web App por administrador, preferencialmente referências a segredos do Azure Key Vault usando Managed Identity e RBAC de leitura estrito, antes de aprovar Deploy. Variáveis obrigatórias: `SPRING_PROFILES_ACTIVE=prod`, `DB_URL=jdbc:postgresql://<host>:5432/<db>?sslmode=require` (adaptar CA/modo de validação TLS ao servidor), `DB_USERNAME`, `DB_PASSWORD`. Nunca passar esses valores como `TF_VAR_*`, CLI com output em logs ou tfvars versionados. As app settings ficam fora do Terraform por `ignore_changes`; alterações nelas não aparecem no plan. No primeiro create apenas `SPRING_PROFILES_ACTIVE=prod` é criado; antes de configurar DB o app pode estar indisponível.

6. `CLYVO_AI_URL` é opcional apenas se a IA não for usada: o fallback `http://localhost:5283` **não serve no App Service**. Para IA, usar endpoint HTTPS alcançável do serviço .NET com proteção/autorização de rede apropriadas; esta infraestrutura não provisiona nem autentica o .NET. `EXPO_PUSH_ENDPOINT` tem default público. Ajustar `JAVA_OPTS`/heap após medir consumo no B1; o app Spring escuta por padrão na porta 8080 e o runtime Java SE faz o encaminhamento. Validar o boot/roteamento no primeiro deploy; não configurar `WEBSITES_PORT` de container customizado para este JAR.

## Execução, aprovação e verificação

Em push/PR filtrado, `Build` roda `./mvnw -B clean verify`, publica relatórios JUnit e `java-api/app.jar`; `TerraformCheck` roda em paralelo fmt, init sem backend e validate **apenas em `infra/app-service`**, mesmo se o build falhar. `infra/bootstrap`, `infra/devops` e `infra/access` são executados/revistos exclusivamente pelo operador. O `Plan` autenticado depende de ambos e ocorre **somente numa execução manual em `main`**, salva um `plan.tfplan` binário da execução e imprime ações. Plans com exclusão/substituição são bloqueados. **Push normal nunca executa plan remoto, apply ou deploy.** Para revisar o primeiro plan, iniciar manualmente pipeline em `main` com `authorizeApply=false` e `authorizeDeploy=false`; para implantar, executar novamente com `authorizeApply=true` e `authorizeDeploy=true`, revisar o *novo plan da mesma execução*, aprovar `ApproveApply`, aguardar `Apply` com o plan salvo, configurar/verificar App Settings e banco, então aprovar `ApproveDeploy` e acompanhar `Deploy` via `AzureWebApp@1`. A aprovação expira e rejeita por default. Recomendável acrescentar checks/approvers independentes em Azure DevOps Environments e limitar quem pode enfileirar execuções com parâmetros de implantação; approvals YAML dependem da proteção da branch/pipeline para não serem removidos por um commit não revisado. Evitar execuções concorrentes usando a mesma key; replanejar se o state mudar entre plan e apply (o apply do plan salvo falha se state foi alterado).

Validar via `https://<web-app>.azurewebsites.net/tutor/ping` e `/v3/api-docs` depois de publicar. `/tutor/ping` é liveness e **não** verifica banco; conferir logs de inicialização, schema validate e operações de leitura com dados fictícios. `https_only` termina TLS no App Service; o app recebe proxy HTTP internamente. Confirmar CORS por origem antes de conectar frontend web: os controllers atuais permitem origens amplas, e não há autenticação real (CPF informado pelo cliente, senhas legadas em claro). Não expor dados reais nem considerar este deploy uma produção segura até corrigir autenticação, senhas, CORS e migrations. Atualizar a baseURL do mobile somente por mudança separada autorizada.

## Custo, rollback e limites

`B1` é plano pago por instância/tempo provisionado, inclusive sem tráfego; estimativa mensal base = preço/hora regional do B1 × ~730 horas × número de instâncias + preço do PostgreSQL externo + backups + egress + Key Vault/Storage de state. `B2/B3/S*` e instâncias extras aumentam essa base. Não existe preço fixo universal: consultar Azure Pricing Calculator para região, moeda e quantidade de instâncias antes de aprovar o plan. Free/Shared não suportam Always On e não são dimensionamento adequado para esta API. Não há slot staging nem troca atômica no B1: rollback do JAR exige reverter o código para o commit aprovado anterior na branch protegida, iniciar **nova execução manual** e aprovar novamente apply (plan sem mudanças) e deploy; guardar o artefato anterior para comparação. O banco exige backup/migração compatível independente, nunca rollback automático de schema. Reversão de Terraform requer novo plan revisado; não executar destroy no pipeline. B1 não inclui disponibilidade avançada nem rede privada configurada aqui; acesso a DB privado pode exigir VNet/subnet/sku e custo adicionais. O App Service não reaproveita o PostgreSQL efêmero do ACI e nenhuma chamada ao Oracle institucional é prevista.
